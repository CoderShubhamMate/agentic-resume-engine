# 03 — JD ANALYSIS, TAILORING AND WRITING STANDARDS

## 3.1 Analyze the JD before editing anything
Write down (in your working notes) for THIS JD only:
- Mandatory requirements
- Minimum Qualifications (MQs), each marked **met** (verified in Master_Data), **partial**, or **gap**
- Preferred requirements, responsibilities
- Technologies, tools, languages
- Education / experience / location / work arrangement
- Important ATS keywords
- Strong verified matches, transferable matches, missing requirements
- **This JD's own emphasis** (its repeated themes, e.g. "clean code", "maintainable software", "API integration", "performance optimization"). The resume must visibly reflect these where truthful.

Every MQ marked "met" must be visible in the top third of the resume (summary, skills, first bullets).
Partial and gap MQs follow 01 section 1.7.

## 3.2 What may change per job
Summary, skill grouping and order, bullet order and wording, project order (names and stacks stay locked, see 02), which certifications to show, and the Areas of Interest section (see 04).

## 3.3 What never changes
Name, contact line, education text, employer names, role titles, dates, project names, project stack sets (see 01 and 02).

## 3.4 Summary
- 2 to 3 sentences: level, core verified stack, one verified strength relevant to this JD.
- It must stay true and sensible if the same resume were sent to a different company.
- **NEVER include the target company name, team, product, or the target job title.**
- **NEVER use cover-letter language:** "eager to", "excited to", "seeking", "looking to", "to join", "at <company>".
- Avoid inflated phrases: results-driven, highly accomplished, expert, extensive experience, passionate, proven ability.
- Match the candidate's real verified experience level (e.g. early-career graduate, mid-level engineer).

## 3.5 Skills
- Only skills supported by Master_Data and allowed by their usage tier (01 section 1.5).
- Group logically (Languages / Web, App / Backend & APIs / Databases / Tools). Put JD-relevant groups and items first.
- No duplicates. No skill bars, stars, percentages or proficiency labels.
- Never add a skill just because the JD asks for it. Unverified relevant skills go to Areas of Interest (04).

## 3.6 Bullets (experience and projects)
- Form: ACTION + TECHNOLOGY/CONTEXT + WORK + PURPOSE/RESULT. One to two lines each.
- XYZ form ("Did X, measured by Y, by doing Z") ONLY when Master_Data has the number. Never invent, estimate or round Y. Without a metric, state a concrete verified outcome (built, tested, integrated, shipped).
- **Exact keyword surfacing:** if a verified technology matches a JD term, use its exact name (e.g. Python, SQL, Postman, Docker) instead of a vague phrase.
- **Appropriate scoping:** use appropriate terminology (e.g. "backend development", "feature implementation", not "enterprise architecture") matching actual experience.
- **No narrative dilution:** do not let unrelated domain skills dominate when the JD is about something else. Lead with what the JD prioritizes.
- Rewording is allowed only if the underlying fact stays the same.

## 3.7 Leadership, coursework, percentages
- Team size, role and scope only as recorded in Master_Data. Never upgrade intern or contributor to lead. Never invent a team size.
- Coursework or academic projects only if in Master_Data, relevant to this JD, one compact line, and the resume stays one page.
- Percentage or GPA only if the JD asks and Master_Data has it (e.g. GPA 3.8 / 85%).

## 3.8 Scannable
- Exactly one page. Most JD-relevant evidence in the first third.
- When space is tight, cut the least relevant content first (never the locked facts).
